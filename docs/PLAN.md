## 1. Философия

- **Отказ лучше иллюзии защищённости.** Нельзя дать гарантию — честно фиксируем «лучшее достижимое» в отчёте.
- Затирание ≠ «35 проходов». NIST SP 800-88: 1 проход + verify достаточен; многопроходность и Gutmann — только opt-in.
- Инструмент сам не создаёт копий данных: без временных файлов, mmap содержимого, plaintext-логов, телеметрии.

## 2. Модель угроз (L0–L4)

| Уровень | Оппонент | Достаточная защита |
|---|---|---|
| L0 | Recuva / testdisk / PhotoRec | 1-проходная перезапись |
| L1 | Продвинутый пользователь, восстановление имён | rename + truncate + per-file TRIM |
| L2 | Коммерческая форензика (EnCase/X-Ways/FTK) на HDD | NIST 800-88 Clear/Purge + verify + гигиена журналов |
| L3 | Лаборатория, магнитная remanence (HDD) | По NIST 800-88 Rev.1 многопроходность почти не даёт; 3 прохода opt-in |
| L4 | Chip-off SSD (FTL, over-provisioning) | Перезапись файла НЕ даёт гарантий; ТОЛЬКО полнодисковое шифрование + уничтожение ключа. В отчёте явный флаг `ssd_chipoff_protected: false` |

Вывод: программа обязана диагностировать шифрование тома, тип носителя и состояние журналов, и объяснять предел гарантий (`vanish check`). Если носитель не зашифрован и это SSD/COW — честный отчёт говорит «без возврата при L0–L2, нет гарантий против chip-off/L3».

## 3. Почему обычное удаление оставляет всё

- unlink снимает только запись каталога; инод/блоки живут до переиспользования.
- Имя остаётся в старых блоках каталога и журнале ФС (ext4 journal, NTFS MFT/USN, APFS).
- Копии: page cache, своп, hiberfil, VSS-тени (Windows), Time Machine/APFS snapshots (macOS).
- SSD: wear leveling + over-provisioning ⇒ перезапись логического блока не трогает старые физические страницы.
- COW-ФС (Btrfs/ZFS/APFS): перезапись создаёт новые экстенты; старые живут в снапшотах.

## 4. Архитектура: ядро + платформенные бэкенды

Ядро НЕ вызывает syscall/WinAPI напрямую. Три трейта:

```rust
trait VolumeProbe {  // ФС, шифрование, rotational, trim, snapshots, COW
    fn probe(path) -> VolumeInfo;
}
trait WipeEngine {   // перезапись + сброс на носитель
    fn open_direct(path) -> Handle;            // O_DIRECT | FILE_FLAG_NO_BUFFERING | F_NOCACHE
    fn overwrite(handle, extents, pattern);
    fn sync(handle);                           // fsync | FlushFileBuffers | fcntl(F_FULLFSYNC)
}
trait Deallocate {
    fn hole_punch(handle, range);              // FALLOC_FL_PUNCH_HOLE | FSCTL_SET_ZERO_DATA | (mac: truncate)
    fn trim_volume(mount);                     // FITRIM | storage-optimization | аппаратный
    fn hide_name(path) -> TempPath;            // renameat | MoveFileEx(WRITE_THROUGH) | rename
}
```

Платформенные crate-ы: `backend-linux`, `backend-windows`, `backend-macos`.
Единое для всех ОС: pipeline, decision, ChaCha20-паттерн, walker, safety, report, check, recovery-scan, aligned-buffer pool.
Единая конвенция хвостов `.vanish-<hex16>` на всех ОС ⇒ один recovery-механизм.

## 6. Конвейер одного файла (единый, все ОС)

```
 1. probe: поддержанная ФС? not symlink/ro/immutable/system-path? nlink? encryption? snapshots? journal active?
 2. ДЕТЕКТ ЗАНЯТОСТИ: скан fd/мэппингов целевого inode (Linux /proc/*/fd, Windows FILE_SHARE_NONE, macOS F_GETLK).
    Если файл открыт другим процессом или mmap'лен — ОТКАЗ с кодом 3, предупреждение в отчёте.
 3. ДЕТЕКТ HARDLINKS: st_nlink > 1 — ОТКАЗ с кодом 3, предупреждение «данные живы по другим путям».
    Каскадное удаление всех имён только флагом --wipe-all-hardlinks.
 4. rename → ".vanish-v1-xxxx" (+fsync каталога)          # прячем оригинальное имя, версия хвоста
 5. open_direct + сверка inode/FileId                       # анти-race, анти-symlink
 6. extents = FIEMAP | FSCTL_GET_RETRIEVAL_POINTERS | (mac: весь файл)
 7. N проходов: overwrite → sync → verify                   # сброс на носитель после КАЖДОГО прохода
 8. SSD → deallocate (punch-hole / SET_ZERO_DATA / truncate)
 9. truncate-to-0 → sync
10. удалить временный каталог-entry (+sync)
11. drop-caches-эквивалент (FADV_DONTNEED / NO_BUFFERING / F_NOCACHE)
12. все потоки данных: NTFS ADS / xattr / resource fork → повторить 4–11 для каждого
13. отчёт: событие, скрытое имя (только хэш или .vanish-v1-xxxx), strategy, bytes, warnings,
    ssd_chipoff_protected, journal_contains_old_names, swap_pages_possible
```

Шаг 12 по умолчанию ВСЕГДА (решение пользователя); opt-out `--keep-streams`.
Исходное имя файла НЕ сохраняется в отчёте в plaintext — только хэш (BLAKE3/SHA-256) или `.vanish-v1-*`, иначе отчёт сам становится форензическим артефактом.

## 7. Матрица стратегий

| Среда | Стратегия | Отчёт |
|---|---|---|
| ext4/xfs/f2fs + HDD | rename → overwrite → truncate | «достаточно» (NIST 800-88) |
| то же + SSD | + PUNCH_HOLE + (opt) FITRIM | «лучшее достижимое; против chip-off/L3 — только шифрование» |
| LUKS / BitLocker / FileVault | обычный конвейер + TRIM | «на носителе шифротекст; совет: стереть ключ» |
| Btrfs/ZFS со снапшотами | отказ или `--accept-cow` | «старые экстенты в снапшотах» |
| NTFS HDD | rename → overwrite → truncate; чистим ADS | как Linux |
| NTFS SSD | + SET_ZERO_DATA (+TRIM) | тот же дисклеймер |
| NTFS + VSS/USN | детект → warning; USN-очистка opt-in (admin) | «копии в тенях; сам их не трогаем» |
| FAT32/exFAT | rename → overwrite → truncate | «журнала нет — плюс» |
| APFS | отказ или `--accept-cow` | «COW: старые блоки могут оставаться в Free Space Map; гарантия только FileVault + гигиена снапшотов» |
| tmpfs/ramfs | unlink достаточно | предупреждение о свопе |
| Своп на той же ФС | отказ | иначе куски уйдут в своп |
| Активный swap (любой раздел) | детект → warning; --disable-swap-for-wipe (root) | «страницы могли быть выгружены в своп» |
| NFS/CIFS/SMB/FUSE/overlay | отказ (`--force-fs`) | нет контроля блоков |
| `/`, `C:\`, системные пути | отказ без `--no-preserve-root` | — |
| `vanish device <блочное устройство>` | NVMe Sanitize / ATA Secure Erase первично; BLKDISCARD только fallback с предупреждением «физическое не гарантировано» | «логическое vs физическое стирание указано явно» |

## 8. Безопасность по платформам

- Windows: refuse C:\Windows, pagefile.sys, hiberfil.sys, swapfile.sys, System Volume Information, RegBack; FILE_FLAG_OPEN_REPARSE_POINT + FILE_SHARE_NONE + сверка FileId; длинные пути `\\?\` с первого дня.
- macOS: refuse /System и системные пути (SIP); детект локальных TM-снапшотов → warning.
- Общее: dirfd/reparse-safe переоткрытие с проверкой ID; юникод-пути; никаких plaintext-логов имён.

## 9. CLI (идентичен на всех ОС)

- `vanish path… [-r] [--xdev]` — основной конвейер
- `vanish freespace <dir>` — затирание свободного места
- `vanish device <dev>` — wipe устройства (подтверждение + проверка «не смонтирован»)
- `vanish check <path>` — диагностика (разрешены read-only exec: fsutil/diskutil/tmutil/nvme)
- `vanish --recovery-scan` — дожимание хвостов `.vanish-*`
- Флаги: `--verify --passes --pattern --dry-run --no-rename --no-trim --json --accept-cow --no-preserve-root --keep-streams --force-fs --wipe-all-hardlinks --disable-swap-for-wipe`

Коды выхода: 0 ок / 1 частично / 2 usage / 3 неподдерживаемая ФС или занятость/хардлинк / 4 IO.

## 10. Тестирование

- Marker-oracle: маркерные паттерны по смещениям → после wipe читаем raw-поверхность (loop-образы Linux; VHD/UDIF в VM) → 0 совпадений.
- Матрица: {ext4, xfs, btrfs, tmpfs, overlayfs} Linux; {NTFS, exFAT, ReFS=отказ} Windows; {APFS, HFS+} macOS.
- Кейсы: sparse, hardlink (отказ по умолчанию, каскад по флагу), дерево, юникод/control-имена, ro, chattr+i / readonly, kill -9 в середине, файл открыт другим процессом (отказ), ADS/xattr, VSS/снапшоты, swap на том же и другом разделе.
- **Forensics-оппонент (обязательно)**: после каждого прогона запускаем PhotoRec, затем testdisk по raw-образу/устройству. Критерий приемки — НОЛЬ восстановимых пользовательских файлов и НОЛЬ имён в recuperación. Любая находка = FAIL-кейс, возвращение на доработку.
- CI: GitHub Actions matrix (3 ОС); ручной forensics-acceptance (PhotoRec/testdisk) в VM.

## 12. Риски и честные границы

1. SSD/COW: per-file перезапись не гарантирует стирание из-за wear leveling, over-provisioning, copy-on-write → честно в `check`; против chip-off/L3 гарантии нет без шифрования + уничтожения ключа. Это физика, не баг.
2. BitLocker-детект без PowerShell — best-effort через WinAPI/реестр; не определили → `Unknown`, а не `Plain`.
3. VSS-тени: сам инструмент их не уничтожает (данные пользователя) — детект + warning + легальные подсказки.
4. APFS: максимум «лучшее достижимое»; гарантия только FileVault + снапшот-гигиена.
5. Журналы (ext4/USN/APFS): имена могли осесть ДО нашего rename → детект журнала + флаг `journal_contains_old_names` в отчёте; опция `--wipe-ext4-journal` требует root/unmount.
6. Своп: страницы могли быть выгружены до начала wiping → детект + warning + опция `--disable-swap-for-wipe` (root).
7. Невозможность гарантировать «без возврата» на незашифрованном SSD против лабораторной форензики (chip-off) — это не баг плана, а фундаментальная граница. План честно фиксирует это в каждом отчёте.

## 13. Анти-scope (не делаем)

- Gutmann-35 по умолчанию (только opt-in legacy), демоны/фоновые службы, криптоконтейнеры, GUI в v1.
- Молчаливое частичное стирание при hardlinks, открытых файлах, активном журнале без флага, swap без флага — всегда отказ или явное предупреждение.
- Главная валюта проекта — честность: утилит, которые не врут пользователю о пределах гарантий, почти нет.

## 14. Security Invariants (неизменяемые правила, violation = автоматический FAIL при приёмке)

1. **Никаких временных файлов инструмента** вне хвостов `.vanish-v1-*` (и recovery-скан их находит).
2. **Никакой записи содержимого целевого файла** в логи/отчёты/stdout/stderr.
3. **Никакого `mmap` целевого файла** — только `open_direct` + `pwrite`/`pread` с выровненными буферами.
4. **`unlink`/`DeleteFile` только после полного `fsync`+`verify` всех проходов** — сначала данные до носителя, потом имя из каталога.
5. **Если `nlink > 1`** — отказ с кодом 3, каскадное удаление всех имён только `--wipe-all-hardlinks`.
6. **Если файл открыт другим процессом / mmap'лен** — отказ с кодом 3, предупреждение в отчёте.
7. **Отчёт никогда не содержит исходных имён в plaintext** — только хэш (BLAKE3/SHA-256) или `.vanish-v1-*`.
8. **Код возврата 4 (IO)** при любой неполной записи или неудачном `fsync` — не маскируем ошибку как успех.
9. **QA-вердикт PASS обязателен перед каждым релизом** — без него релиза не существует.

## 15. Мультиагентная модель разработки

План реализуется не «одним исполнителем», а через оркестрацию агентов. Мотивация: в проекте, где продукт обещает «данные не восстановить», самый опасный баг — тот, что не видит автор кода. Поэтому (а) главный агент принимает/проверяет каждую единицу работы, (б) финальную проверку делает агента-проверяльщик с полностью чистым контекстом, порождающий свои тестовые файлы/каталоги.

### 14.1. Роли

```
                    ОРКЕСТРАТОР (главный агент)
                    план · контракт · приёмка · эскалации
                                 │
     ┌───────────┬───────────────┼───────────────────┬──────────────┐
 архитектор   core-dev      backend-devs         тест-инженер      QA-агент
  (M0)       (M1)        linux/windows/macos    (M3/M5/M7)     (final gate)
```

| Роль | Ответственность | Момент |
|---|---|---|
| **Оркестратор (главный)** | Держит утверждённый план; нарезает фазы M0–M7 на task-brief-ы; создаёт суб-агентов, принимает или возвращает работу на доработку; единственный, кто меняет контракт; эскалирует пользователю при затруднениях | постоянно |
| **Архитектор** | M0: threat-model.md, контракт трейтов, JSON-schema отчёта | M0 |
| **Core-dev** | vanish-core + vanish-cli (safety, pipeline, pattern, report) | M1 |
| **Backend-devs** (×3) | backend-linux / backend-windows / backend-macos строго по контракту | M2, M4, M6 |
| **Тест-инженер** | Harness: loop-ФС, marker-oracle, матрица кейсов. Пишет тесты ДО/ПАРАЛЛЕЛЬНО реализации (красные → зелёные) | M3, M5, M7 |
| **QA-агент (final gate)** | Независимая приёмка релиза: сам порождает атакующий корпус, гоняет готовый бинарь, сканирует raw-поверхности, выдаёт вердикт. НИЧЕГО не знает о процессе разработки (fresh context, без общения с dev-агентами) | перед каждым релизом |

### 14.2. Цикл задачи (brief → исполнение → приёмка → доработка)

1. Оркестратор выдаёт **task-brief**: цель, ссылка на контракт, Definition of Done, список запрещённых зон (security-invariants: никаких временных файлов, никаких plaintext-логов, никакого exec вне разрешённого списка), пути файлов.
2. Суб-агент исполняет и возвращает отчёт: diff, запуск тестов, соответствие DoD по пунктам.
3. Оркестратор проверяет **три уровня приёмки** (это и есть «чуть проверяю, получая действительно хороший результат»):
   - (a) механика: build + clippy `-D warnings` + unit-тесты зелёные;
   - (b) diff-ревью: не нарушены контракт и security-invariants, стиль согласован с кодовой базой;
   - (c) факты: DoD закрыт по пунктам, никаких «незакрытых разъёмов» (TODO-мостей под DoD).
4. Не принято → возврат на доработку с конкретным списком дефектов. **Максимум 2 цикла доработки** → третий провал = эскалация пользователю с диагностикой (diff, логи, гипотеза причины).
5. Принято → оркестратор обновляет карту прогресса в плане.

### 14.3. Контракт прежде всего; параллельность

- После M0 контракт (трейты + JSON-schema) «замораживается» как файл в репо — единственный источник истины; change только через оркестратора, с записью в changelog контракта.
- Тест-инженер компилирует кейсы против контракта ещё до реализации (проверяемо красные тесты) — суб-агенты не могут «сдать» код, который проходит их собственные слабые тесты.
- После заморозки контракта фазы идут **строго последовательно** (решение пользователя): один суб-агент за раз, полная приёмка оркестратором перед запуском следующего. Тест-харнесс пишется до/вместе с бэкендами, но исполнение по одному агенту; оркестратор — единственная точка слияния общих файлов (Cargo workspace, CI).

### 14.4. QA-gate — финальная стадия (явное требование пользователя)

Перед КАЖДЫМ релизом (v1.0/v1.1/v1.2) поднимается QA-агент с чистым контекстом. Его протокол:

1. **Корпус атак** (генерирует сам, без подсказок из dev-процесса):
   - файлы с маркерными паттернами по смещениям (посекторно различимые);
   - конфликтные имена: unicode, control-символы, emoji, длина на границе;
   - sparse-файлы, hardlinks (nlink>1), symlinks, immutable-файлы, ro-каталоги;
   - деревья произвольной глубины; файлы «горячие» (открытые другим процессом);
   - ADS/xattr-тайники (Windows/macOS), потоки суммы > 1 потока.
2. **Исполнение**: гоняет готовый бинарь по корпусу всеми режимами (file/dir/freespace/check/recovery-scan), включая kill -9 в середине прогона и последующий --recovery-scan.
3. **Forensics-проверка** (обязательный шаг, решено): (а) посекторный скан raw-образа/устройства на маркеры → критерий **«0 совпадений»**; (б) прогон **реальных инструментов восстановления** (PhotoRec, затем testdisk) по корпусу и по образу — они должны вернуть НОЛЬ восстановимых пользовательских файлов/имен. Их находки = FAIL-кейс.
4. **Гигиена инструмента**: коды выходов корректны; JSON-схема совпадает с контрактом; у инструмента НЕТ собственных хвостов (временных файлов, логов с содержимым, права не изменились у несвязанных файлов).
5. **Вердикт**: `qa-verdict-<release>.md` — PASS/FAIL по каждому кейсу + сводный вердикт. FAIL → оркестратор ставит задачи на фиксы → новый QA-цикл.

**Релиз без PASS-вердикта от QA-агента невозможен.** Это часть DoD каждого релиза, а не «лучшая практика».

### 14.5. Артефакты коммуникации (в репо, для ревью человеком)

- `docs/tasks/task-brief-<id>.md` — что и зачем выдаётся суб-агенту.
- `docs/qa/qa-verdict-<release>.md` — вердикт gate-агента.
- `docs/contract/` — замороженный контракт трейтов + JSON-schema + changelog.
- Журнал эскалаций — все вопросы к пользователю с контекстом и предложенными вариантами.

### 14.6. Коммуникационные правила для оркестратора

- Суб-агенту всегда передавать: путь к плану, путь к контракту, DoD, security-invariants, «не выходи за рамки каталогов проекта».
- Суб-агенты исполняются строго последовательно, по одному; ни один суб-агент не правит общие файлы (workspace, CI) — общие файлы меняет только оркестратор.
- Затруднение, не решённое за 2 попытки, или вопрос уровня продукта (не кода) → сразу вопрос пользователю, не молчаливое обходное решение.
