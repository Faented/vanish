## 1. Цели и не-цели проекта

### 1.1. Основная цель

**Deletion with no recovery**: после успешного стирания содержимое и имена пользовательских файлов не могут быть восстановлены на всех уровнях угроз, где `vanish` может *честно* дать гарантию (уровни — раздел 3; границы по ФС — раздел 5). «Честно» — ключевое слово: уровень обещания всегда совпадает с тем, что написано в отчёте конкретного запуска.

### 1.2. Цели (C1–C7)

| # | Цель | Формулировка |
|---|---|---|
| C1 | Уничтожение содержимого | Содержимое файла на носителе не может быть восстановлено средствами оппонента данного уровня (NIST SP 800-88 Clear/Purge + verify: 1 проход + verify достаточно; многопроходность — только opt-in) |
| C2 | Уничтожение имён | Имя файла должно исчезнуть из каталога, инода/метаданных и — насколько это возможно — из журналов ФС; своему артефакту-отчёту имя в plaintext запрещено |
| C3 | Отчёт как контракта часть | Каждый запуск завершается отчётом: событие, скрытое имя (только хэш BLAKE3/SHA-256 или хвост `.vanish-v1-*`), strategy, bytes, warnings и флаги `ssd_chipoff_protected`, `journal_contains_old_names`, `swap_pages_possible` |
| C4 | Refuse-over-promise | Отказ лучше иллюзии защищённости: если гарантия недостижима — честный отказ (код 3) либо явно помеченное «лучшее достижимое»; никогда «успех» с молчаливой границей |
| C5 | Минимализм по NIST SP 800-88 | Один проход с проверкой как база; Gutmann-35 и мультипроходность — opt-in legacy, не дефолт и не маркетинг |
| C6 | Инструмент не множит данные | Никаких временных файлов (кроме хвостов `.vanish-v1-*`), никакого `mmap` содержимого целевого файла, никаких plaintext-логов, никакой телеметрии |
| C7 | Предсказуемость отказов | Любая недоделка — код 1/3/4 и предупреждение, никогда не маскируется под успех; «молчаливое частичное стирание» запрещено по определению |

### 1.3. Не-цели (анти-цели)

`vanish` — инструмент точечных гарантий, а не «универсальный стиратель риска». Что он *не* делает и никогда не будет делать:

| # | Не-цель | Пояснение |
|---|---|---|
| N1 | **Не резервное копирование** | Не создаёт, не восстанавливает и не затирает бэкапы. Копии данных вне целевого носителя (внешние диски, NAS, Time Machine, облачные копии) — зона ответственности пользователя до запуска |
| N2 | **Не hardening живой системы** | Не «лечит» ОС: не выключает своп постоянно, не чистит VSS-тени за пользователя, не трогает снапшоты (данные пользователя); только диагностика + предупреждения + отдельные явные opt-in опции из плана |
| N3 | **Не «стирает всё подряд»** | Системные пути, корень диска, `C:\Windows`, `/System` и т.п. запрещены без явного переопределяющего флага; ReFS и неизвестные ФС — отказ |
| N4 | **Не Gutmann-35 по умолчанию** | Многопроходность и Gutmann — opt-in; дефолт — 1 проход + verify (NIST SP 800-88) |
| N5 | **Не криптоконтейнер и не GUI** | Никаких демонов/фоновых служб, криптоконтейнеров, GUI в v1; только CLI (+ JSON-отчёты) |
| N6 | **Не «магия против физики»** | Не «отменяет» wear leveling, over-provisioning, copy-on-write; на SSD/COW честно фиксирует физический предел и пишет в отчёт |
| N7 | **Не закрывает прошлое** | Если копия данных уже ушла в своп/журнал/снапшот/бэкап/облако *до* запуска — `vanish` может предупредить, но не стереть |

### 1.4. Идеологическая ось: отказ против обещания

- База — план §1: **«Отказ лучше иллюзии защищённости»**. Нельзя дать гарантию — честно фиксируем «лучшее достижимое» в отчёте.
- План §13: «молчаливое частичное стирание» при hardlinks, открытых файлах, активном журнале без флага, свопе без флага — запрещено; всегда отказ или явное предупреждение.
- План §13: «Главная валюта проекта — честность: утилит, которые не врут пользователю о пределах гарантий, почти нет». Это осознанная позиция продукта, а не риторика.

### 1.5. Опора: Security Invariants (из плана §14)

Неизменяемые правила; нарушение любого — автоматический FAIL при приёмке. Сводно (полная формулировка — план §14 и будущий контракт):

1. Никаких временных файлов инструмента вне хвостов `.vanish-v1-*`; recovery-скан их находит.
2. Никакой записи содержимого целевого файла в логи/отчёты/stdout/stderr.
3. Никакого `mmap` целевого файла — только `open_direct` + `pwrite`/`pread` с выровненными буферами.
4. `unlink`/`DeleteFile` только после полного `fsync`+`verify` всех проходов: сначала данные до носителя, потом имя из каталога.
5. `nlink > 1` — отказ с кодом 3; каскадное удаление всех имён только флагом `--wipe-all-hardlinks`.
6. Файл открыт другим процессом / mmap'лен — отказ с кодом 3, предупреждение в отчёте.
7. Отчёт никогда не содержит исходных имён в plaintext — только хэш (BLAKE3/SHA-256) или `.vanish-v1-*`.
8. Код возврата 4 (IO) при любой неполной записи или неудачном `fsync` — ошибка не маскируется как успех.
9. QA-вердикт PASS обязателен перед каждым релизом — без него релиза не существует.

## 2. Активы

### 2.1. Что мы защищаем

Определение: актив — всё, что оппонент может использовать для восстановления удалённых данных или реконструкции того, что пользователь делал.

| # | Актив | Что в нём ценного | Против кого важен | Реакция `vanish` |
|---|---|---|---|---|
| A1 | Содержимое пользовательских файлов | Байты данных в экстентах на носителе | L0–L4 (восстановление данных) | Перезапись по экстентам (direct I/O, мимо кэша) → сброс на носитель после каждого прохода → verify → truncate → deallocate на SSD |
| A2 | Имена и пути (метаданные) | Записи каталогов, инод/MFT-записи, индексы каталогов, записи журналов ФС | L0–L2 (восстановление имён и структуры каталогов) | rename → временный хвост `.vanish-v1-<hex16>` + fsync каталога → перезапись → truncate → удаление записи; plaintext имён в отчёте запрещён |
| A3 | Потоки данных (ADS / xattr / resource fork) | Тайники: Zone.Identifier, теги, иконки, произвольные пользовательские данные | L0–L2 | Стираются **всегда по умолчанию**; opt-out только `--keep-streams`; для каждого потока повторяется полный конвейер |
| A4 | Собственные артефакты `vanish` | Отчёты, временные имена `.vanish-v1-*`, буферы процесса | L1–L2 (сам инструмент как источник утечки) | Инвариант 1–3, 7: без временных файлов вне хвостов, без mmap-содержимого, без plaintext-логов; отчёт называет файлы только хэшем или хвостом |
| A5 | Состояние среды (кэши/своп/журналы) | Page cache, своп-страницы, записи журналов ФС, кэши контроллера | L2–L4 | open_direct мимо кэша (O_DIRECT / FILE_FLAG_NO_BUFFERING / F_NOCACHE), drop-caches-эквивалент в конце, детект свопа и журналов + честные флаги в отчёте |

### 2.2. Активы вне зоны ответственности (принципиально не трогаем)

- Системные данные ОС: `C:\Windows`, `System Volume Information`, RegBack, `/System` и прочее из списков отказа (план §8) — vanish их защищает *от самого пользователя*, отказываясь стирать.
- Снапшоты и копии: VSS-тени, Time Machine, локальные APFS-снапшоты — «данные пользователя», vanish сам их не уничтожает (план §12.3): детект → warning → легальные подсказки.
- Бэкапы и облачные копии — вне продукта (N1).
- Собственных копий данных vanish не создаёт вообще (инвариант 1) — значит «актив A6: копии vanish» не существует по построению.

## 3. Модель угроз L0–L4

### 3.0. Шкала (дословно из плана §2)

| Уровень | Оппонент | Достаточная защита |
|---|---|---|
| L0 | Recuva / testdisk / PhotoRec | 1-проходная перезапись |
| L1 | Продвинутый пользователь, восстановление имён | rename + truncate + per-file TRIM |
| L2 | Коммерческая форензика (EnCase/X-Ways/FTK) на HDD | NIST 800-88 Clear/Purge + verify + гигиена журналов |
| L3 | Лаборатория, магнитная remanence (HDD) | По NIST 800-88 Rev.1 многопроходность почти не даёт; 3 прохода opt-in |
| L4 | Chip-off SSD (FTL, over-provisioning) | Перезапись файла НЕ даёт гарантий; ТОЛЬКО полнодисковое шифрование + уничтожение ключа. В отчёте явный флаг `ssd_chipoff_protected: false` |

Вывод плана §2 (обязателен для реализации): программа обязана диагностировать шифрование тома, тип носителя и состояние журналов и объяснять предел гарантий — это делает `vanish check`. Если носитель не зашифрован и это SSD/COW — честный отчёт говорит: «без возврата при L0–L2, нет гарантий против chip-off/L3».

Ниже каждый уровень раскрыт по четырём вопросам: кто оппонент, чем вооружён, что мы делаем, чего мы **не** можем сделать.

### 3.1. L0 — бытовое восстановление

- **Оппонент.** Случайный получатель носителя, коллега, покупатель б/у диска; человек, который поставил «рекавери-утилиту» из топа поисковика. Навыков и оборудования — минимум; времени — один вечер.
- **Инструменты.** Recuva, testdisk, PhotoRec; навигация по «удалённым файлам», сигнатурный поиск «по кусочкам».
- **Оборона vanish.** Однопроходная перезапись содержимого + verify (шаг 7 конвейера), сброс на носитель после каждого прохода; переименование в `.vanish-v1-*` до перезаписи и удаление имени после (шаги 4, 10); truncate и — на SSD — deallocate. Этого достаточно против L0 по NIST SP 800-88.
- **Чего не защищаем.** Копии, существующие вне целевого файла: бэкапы, облачные копии, снапшоты, выгрузки в своп — L0-инструменты найдут их без труда; vanish против копий предупреждает, но не стирает (N1, N7).

### 3.2. L1 — продвинутый пользователь, восстановление имён

- **Оппонент.** IT-администратор, технически грамотный «исследователь»; понимает, что имя файла живёт в метаданных, а не только в каталоге.
- **Инструменты.** Просмотр MFT и USN-журнала NTFS, парсеры каталогов ext4/APFS, поиск именных строк в нераспределённом пространстве, autopsy-подобные утилиты.
- **Оборона vanish.** rename в хвост `.vanish-v1-<hex16>` + fsync каталога (имя прячется ещё до перезаписи); truncate-to-0; per-file TRIM на SSD; гигиена журналов по возможности: для ext4 — опция очистки журнала (root/unmount), для NTFS — USN-очистка opt-in (admin); постоянные предупреждения о VSS/TM/APFS-снапшотах.
- **Чего не защищаем.** Имена и фрагменты, которые осели в журнале/USN/старых блоках каталога **до** запуска vanish — это фиксируется флагом `journal_contains_old_names`, а не замалчивается. Имена внутри снапшотов — вне досягаемости.

### 3.3. L2 — коммерческая цифровая форензика на HDD

- **Оппонент.** Продуктовая лаборатория / служба реагирования на инциденты / правоохранительные эксперты с коммерческим софтом и методиками.
- **Инструменты.** EnCase, X-Ways, FTK; полный анализ «сырой» поверхности HDD, журналов, времён, теневых копий; судебно-экспертные заключения.
- **Оборона vanish.** Стратегия NIST 800-88 Clear/Purge + verify на HDD; строгая гигиена журналов (детект + флаги + явные опции); полный запрет plaintext-имён в собственных артефактах; отказ от работы в состояниях, где гарантия была бы ложной (занятость, hardlinks, своп на той же ФС, COW, сети) — то есть никаких «полусостояний», по которым L2-эксперт восстановил бы историю.
- **Чего не защищаем.** HDD — защищаем; всё остальное: SSD (см. L4), COW-ФС со снапшотами, теневые копии, своп-страницы, выгруженные раньше. На HDD честная позиция: «достаточно» — при условии, что предупреждения отчёта разрешены пользователем (нет активного свопа/журнала без опции и пр.).

### 3.4. L3 — лаборатория, магнитная remanence (HDD)

- **Оппонент.** Государственного уровня лаборатория с физическим доступом к вскрытому диску; цель — прочитать «остаточную намагниченность» после перезаписи.
- **Инструменты.** Разбор пластин, магнитный микроскоп, дорогое оборудование и месяцы времени; экономика атаки оправдана только при высокой ценности данных.
- **Оборона vanish.** По NIST SP 800-88 Rev.1 многопроходная перезапись *почти не даёт* приращения защищённости против такой атаки. vanish поддерживает opt-in 3 прохода (и legacy-мультипроход как opt-in), но никогда не продаёт это как гарантию против L3 — в противовес маркетингу «35 проходов».
- **Чего не защищаем.** Формальной защиты против remanence-экспертизы инструмент не даёт и не обещает: она достигается уничтожением носителя или полнодисковым шифрованием с уничтожением ключа — за пределами ответственности `vanish file`. В отчёте это отражено стратегией «достаточно (NIST 800-88)» с предупреждениями, но без слова «гарантия против L3».

### 3.5. L4 — chip-off SSD (FTL, over-provisioning)

- **Оппонент.** Аппаратная лаборатория: снятие NAND-чипов с платы и чтение их напрямую, минуя логику носителя.
- **Инструменты.** Chip-off-ридеры, реверс FTL (реконструкция словаря логических→физических адресов), доступ к областям over-provisioning, кэшам контроллера, «провалившимся» страницам прошивок.
- **Почему перезапись файла не помогает.** При перезаписи логического блока FTL обычно размещает новые данные на *новые* физические страницы (wear leveling), а старые страницы остаются в over-provisioning-области и в регионах, выведенных из активного пула. TRIM/punch-hole — это подсказка контроллеру, а не приказ «стёртые страницы физически обнулить»; физически старые страницы могут пережить и после этого. Это физика носителя, а не недоработка стратегии (план §12.1).
- **Оборона vanish.** Честный отчёт: на незашифрованном SSD флаг `ssd_chipoff_protected: false` появляется **в каждом отчёте**. Единственное реальное противоядие — полнодисковое шифрование (LUKS / BitLocker / FileVault), включённое так, что на носителе хранится только шифротекст: тогда chip-off получает шифротекст без ключа. vanish детектирует шифрование тома и в отчёте советует «стереть ключ» (план §7, строка LUKS/BitLocker/FileVault). Деаллокация (punch-hole / SET_ZERO_DATA / truncate) + TRIM/FITRIM выполняются как «лучшее достижимое», но не как гарантия.
- **Чего не защищаем.** Незашифрованный SSD от chip-off — не защищаем никак. Это фундаментальная граница продукта (план §12.7), а не баг плана. Повторим формулу: **на незашифрованном SSD гарантия против лабораторной форензики невозможна без полнодискового шифрования.**

### 3.6. Что вне модели угроз

Следующее не относится к уровням L0–L4 и не входит в обещания продукта:

- Компрометация самой ОС (rootkit, вредонос, подменённый бинарник `vanish`) — защита «от злой системы» не предусмотрена; предположение A3 (раздел 7).
- Физический доступ оппонента *во время* работы vanish (выдёргивание диска, принуждение) — предположение A5.
- Прошлое пользователя: копии, покинувшие носитель раньше (бэкапы, облако, чужие машины) — нецели N1/N7.
- Атаки на инфраструктуру поставки (пакеты, сборки, каналы доставки бинарника) — область распространения, не угроза-модель продукта.

### 3.7. Как читать уровни на практике

Примеры сценариев и соответствующих им уровней (использовать при разборе отчётов и багрепортов):

| Сценарий | Уровень | Заявление vanish |
|---|---|---|
| «Файл можно вернуть программой-рекавер», случайные люди ищут свободный диск | L0 | Гарантия «достаточно» на HDD; на SSD — «лучшее достижимое» с `ssd_chipoff_protected: false` |
| «Специалист собрал имена удалённых файлов из MFT/USN» | L1 | rename + truncate + per-file TRIM; честный флаг `journal_contains_old_names`, если имена осели в журнале до запуска |
| «Коммерческая форензика вскрыла HDD и восстановила содержимое» | L2 | NIST Clear/Purge + verify + гигиена журналов; заявление «достаточно» действует на HDD при соблюдении предположений (раздел 7) и отсутствии отказных условий (раздел 8) |
| «Лаборатория прочла данные с пластин после перезаписи» | L3 | Не обещаем и не продаём мультипроходность как гарантию |
| «Незашифрованный SSD уехал в лабораторию, чипы сняты» | L4 | Гарантии нет: флаг `ssd_chipoff_protected: false` в каждом отчёте; противоядие — полнодисковое шифрование + уничтожение ключа |
| «Данные нашли в облачной копии/бэкапе» | вне шкалы | Нецель N1; vanish предупреждает о границе ответственности, но не действует там |

## 4. Карта мест хранения данных

Ключевая идея плана §3: **обычное удаление (unlink/DeleteFile) оставляет всё**. Ниже — карта всех мест, где данные «живут дольше, чем пользователь думает», и реакция vanish на каждое.

Мотивация (план §3, кратко):

- unlink снимает только запись каталога; инод/блоки живут до переиспользования.
- Имя остаётся в старых блоках каталога и в журнале ФС (ext4 journal, NTFS MFT/USN, APFS).
- Копии: page cache, своп, hiberfil, VSS-тени (Windows), Time Machine/APFS snapshots (macOS).
- SSD: wear leveling + over-provisioning ⇒ перезапись логического блока не трогает старые физические страницы.
- COW-ФС (Btrfs/ZFS/APFS): перезапись создаёт новые экстенты; старые живут в снапшотах.

### 4.0. Легенда

- **Да** — vanish гарантированно работает с этим местом на соответствующем уровне угроз.
- **Частично** — vanish выполняет доступные действия, но полное исчезновение не гарантируется; в отчёте появляются предупреждение и/или флаг.
- **Нет** — vanish не имеет доступа или принципиально не трогает; честно объявляет предел и (если применимо) отказывается.

### 4.1. На том же носителе — файловая система

| Место | Что там лежит | vanish может? | Реакция инструмента |
|---|---|---|---|
| Экстенты данных файла | Содержимое | **Да** | open_direct (O_DIRECT / FILE_FLAG_NO_BUFFERING / F_NOCACHE) → перезапись по списку экстентов (FIEMAP / FSCTL_GET_RETRIEVAL_POINTERS / весь файл на macOS) → sync после каждого прохода → verify → truncate-to-0 → sync |
| Записи каталога (старые имена) | Имя + указатель на инод | **Частично** | rename отдельно: сначала имя прячется в хвост `.vanish-v1-<hex16>` (+fsync каталога), затем, после стирания данных, запись удаляется (+sync). Старые записи каталога исчезают гарантированно только при переиспользовании блоков — предел фиксируется отчётом |
| Инод / MFT-запись / APFS-метаданные | Размер, время, ссылки | **Частично** | Данные затираются, метаданные освобождаются; реконструкция «что было» по метаданным гасится удалением записи (шаг 10) |
| Журнал данных ФС (ext4 journal) | Копии блоков/имён, осевшие ДО и ВО ВРЕМЯ стирания | **Частично** | Детект активного журнала; флаг `journal_contains_old_names`; полная очистка журнала — отдельная опция, требующая root/unmount (план §12.5). Без неё vanish не обещает стирания имён в журнале |
| NTFS MFT + $LogFile + USN-журнал | Копии записей, история операций с файлами | **Частично** | Детект; USN-очистка opt-in (admin); предупреждение «копии в тенях; сам их не трогаем» для VSS |
| APFS-транзакции + Free Space Map | Старые версии блоков COW | **Частично/Нет** | См. COW-строку в 4.4: «старые блоки могут оставаться в Free Space Map; гарантия только FileVault + гигиена снапшотов» |
| Индексы каталогов (NTFS $I30, ext4 dx, APFS btree) | Копии имён | **Частично** | Покрываются rename→truncate→unlink с fsync; «старые» копии имён в индексных страницах — тот же предел, что у журналов |
| ADS / xattr / resource fork | Потоки-тайники | **Да** | Шаг 12: полный повтор конвейера для каждого потока; всегда по умолчанию, opt-out `--keep-streams` |
| Sparse-области | «Дырки» файла | **Да** | Отсутствующие экстенты не хранят данных; deallocate освобождает их физически (на SSD) |
| tmpfs/ramfs | Всё в памяти | **Да** | unlink достаточно; предупреждение о свопе (план §7) |

### 4.2. В памяти ОС и ядра

| Место | Что там лежит | vanish может? | Реакция инструмента |
|---|---|---|---|
| Page cache | Страницы содержимого и метаданных | **Частично** | Запись выполняется мимо кэша (O_DIRECT / FILE_FLAG_NO_BUFFERING / F_NOCACHE); шаг 11 — drop-caches-эквивалент (FADV_DONTNEED / NO_BUFFERING / F_NOCACHE). Страницы, попавшие в кэш ранее чужими процессами, vanish не вытесняет — осознанный предел |
| Своп (Linux: раздел/файл; Windows: pagefile.sys, swapfile.sys; macOS: директории свопа) | Выгруженные страницы содержимого; постраничная память | **Нет** (для уже выгруженного) | Детект → предупреждение в отчёте: флаг `swap_pages_possible` («страницы могли быть выгружены в своп»); опция `--disable-swap-for-wipe` (root) — временно отключить своп и восстановить после. Своп на **той же ФС** = отказ (план §7): иначе куски могут быть выгружены прямо во время перезаписи |
| hiberfil.sys (файл гибернации: слепок оперативной памяти) | Содержимое памяти, включая кэши файлов | **Нет** | Путь входит в список системных отказов Windows (план §8); vanish не пишет в него и предупреждает в `check`, что гибернация — среда хранения |
| Анонимная память процесса vanish | Буферы с паттернами и читаными блоками | **Частично** | Инвариант 3 запрещает `mmap` целевого файла: содержимое пишется только в выровненные буферы и сразу на носитель. Ядро может выгрузить страницы процесса в своп — ограничить это из пользовательского пространства нельзя; флаг `swap_pages_possible` честно сигнализирует о такой среде |

### 4.3. Внутри носителя (SSD-специфика)

| Место | Что там лежит | vanish может? | Реакция инструмента |
|---|---|---|---|
| FTL-словарь (логика→физика) | Карта, по которой chip-off восстанавливает файлы | **Нет** | Не доступен из ОС; учитывается в честном отчёте |
| Старые физические страницы (wear leveling) | Предыдущие версии блоков | **Нет** | Перезапись логического блока не трогает их (план §3); deallocate — «лучшее достижимое» |
| Over-provisioning area | Запасные страницы, в которых FTL прячет старые данные | **Нет** | Не адресуемо; причина флага `ssd_chipoff_protected: false` |
| Кэши/буферы контроллера (SLC-кэш и пр.) | Ещё не зафиксированные в NAND данные | **Нет** | sync (fsync / FlushFileBuffers / F_FULLFSYNC) минимизирует окно, но не доказывает физическую фиксацию — поэтому окончательное мерилом остаётся verify; несоответствие даёт код 4 |
| Физическая поверхность после deallocate (punch-hole / SET_ZERO_DATA / truncate + TRIM/FITRIM) | «Свободные» страницы | **Частично** | Это лучшие подсказки контроллеру; но только полнодисковое шифрование даёт гарантию против chip-off; `--no-trim` отключает избыточный TRIM по желанию |
| Блочное устройство целиком (`vanish device`) | Все логические блоки | **Да (логическое) / Частично (физическое)** | NVMe Sanitize / ATA Secure Erase — первичный путь (с подтверждением и проверкой «не смонтирован»); BLKDISCARD — только fallback с предупреждением «физическое не гарантировано»; логическое vs физическое стирание указано явно (план §7) |

### 4.4. Вне досягаемости vanish (копии, снапшоты, облака)

| Место | Что там лежит | vanish может? | Реакция инструмента |
|---|---|---|---|
| COW-ФС: Btrfs/ZFS | Старые экземпляры экстентов в снапшотах и во внешнем пространстве | **Нет** | Отказ или `--accept-cow`; предупреждение «старые экстенты в снапшотах» (план §7, §12) |
| COW-ФС: APFS | Старые блоки в снапшотах / Free Space Map | **Нет** | Отказ или `--accept-cow`; формулировка отчёта: «COW: старые блоки могут оставаться в Free Space Map; гарантия только FileVault + гигиена снапшотов» |
| VSS-тени (Windows, System Volume Information) | Точечные копии тома | **Нет** | Детект → warning; сам инструмент тени не уничтожает (данные пользователя); «сам их не трогаем» + легальные подсказки (план §7, §12.3) |
| Time Machine (внешний диск) и локальные APFS-snapshots | Полные копии файлов | **Нет** | Детект локальных TM-снапшотов → warning (план §8); пользователь сам решает, что делать с копиями |
| Резервные копии (внешние диски, NAS, образы) | Полные копии файлов | **Нет** | Нецель N1; vanish не сканирует и не трогает несвязанные носители |
| Облачная синхронизация (OneDrive, Dropbox, Google Drive, iCloud Drive и пр.) | Копии в облаке + локальный кэш клиента | **Нет** | vanish не обнаруживает клиентов синхронизации и ничего не затирает в них — вне продукта (N1); риск остаётся на пользователе |
| Копии реестра (RegBack) и прочие системные данные Windows | Системные файлы | **Нет** | Список системных отказов Windows; vanish не стирает (защита пользователя от себя) |

### 4.5. Специальные/неподдерживаемые ФС

| Место | vanish может? | Реакция инструмента |
|---|---|---|
| NFS / CIFS / SMB | **Нет** | Отказ — «нет контроля блоков»; возможен только по `--force-fs` (план §7) |
| FUSE / overlayfs | **Нет** | Отказ — «нет контроля блоков»; `--force-fs` как исключение |
| ReFS и неопознанные ФС | **Нет** | Отказ (матрица тестов план §10: ReFS = отказ); `vanish check` называет причину |

### 4.6. Сводка «самое опасное»

Три места, где данные живут *обязательно* дольше перезаписи и о которых vanish молчать не вправе: (1) журнал ФС с именами до запуска — флаг `journal_contains_old_names`; (2) своп с выгруженными страницами — флаг `swap_pages_possible`; (3) снапшоты/копии вне носителя — предупреждения и, для COW, отказ без `--accept-cow`. И одно место, где гарантия фундаментально невозможна: незашифрованный SSD против chip-off — флаг `ssd_chipoff_protected: false`.

## 5. Гарантии и честные границы

### 5.1. Матрица стратегий (дословно из плана §7)

| Среда | Стратегия | Отчёт |
|---|---|---|
| ext4/xfs/f2fs + HDD | rename → overwrite → truncate | «достаточно» (NIST 800-88) |
| то же + SSD | + PUNCH_HOLE + (opt) FITRIM | «лучшее достижимое; против chip-off/L3 — только шифрование» |
| LUKS / BitLocker / FileVault | обычный конвейер + TRIM | «на носителе шифротекст; совет: стереть ключ» |
| Btrfs/ZFS со снапшотами | отказ или `--accept-cow` | «старые экстенты в снапшотах» |
| NTFS HDD | rename → overwrite → truncate; чистим ADS | как Linux |
| NTFS SSD | + SET_ZERO_DATA (+TRIM) | тот же дисклеймер |
| NTFS + VSS/USN | детект → warning; USN-очистка opt-in (admin) | «копии в тенях; сам их не трогаем» |
| FAT32/exFAT | rename → overwrite → truncate | «журнала нет — плюс» |
| APFS | отказ или `--accept-cow` | «COW: старые блоки могут оставаться в Free Space Map; гарантия только FileVault + гигиена снапшотов» |
| tmpfs/ramfs | unlink достаточно | предупреждение о свопе |
| Своп на той же ФС | отказ | иначе куски уйдут в своп |
| Активный swap (любой раздел) | детект → warning; `--disable-swap-for-wipe` (root) | «страницы могли быть выгружены в своп» |
| NFS/CIFS/SMB/FUSE/overlay | отказ (`--force-fs`) | нет контроля блоков |
| `/`, `C:\`, системные пути | отказ без `--no-preserve-root` | — |
| `vanish device <блочное устройство>` | NVMe Sanitize / ATA Secure Erase первично; BLKDISCARD только fallback с предупреждением «физическое не гарантировано» | «логическое vs физическое стирание указано явно» |

### 5.2. Значения слов в колонке «Отчёт»

- **«достаточно»** — стратегия достигает заявленного уровня против L0–L2 на HDD при выполнении предположений (раздел 7); это норма NIST SP 800-88 Clear/Purge + verify, а не «сотрём навсегда всеми возможными способами».
- **«лучшее достижимое»** — vanish выполняет все доступные логические действия (перезапись, деаллокация, TRIM), но физика носителя (SSD FTL, COW) ограничивает результат; в отчёте всегда стоит дисклеймер про chip-off/L3.
- **«отказ»** — vanish не начинает операцию (код 3), пока пользователь явно не разрешит (`--accept-cow`, `--force-fs`, `--no-preserve-root`, `--wipe-all-hardlinks`, `--disable-swap-for-wipe`, опция журнала).
- **детект → warning** — операция выполняется, но отчёт обязан содержать предупреждение и соответствующий флаг; «успех» без предупреждений в такой ситуации — нарушение инвариантов.

### 5.3. Явные невозможности (читать вслух при ревью)

1. **На незашифрованном SSD гарантия против лабораторной форензики (chip-off) невозможна без полнодискового шифрования.** vanish повторяет это в каждом отчёте через флаг `ssd_chipoff_protected: false` (план §2, §12.7). Это физика, не баг плана.
2. **COW-ФС со снапшотами:** старые экстенты переживают перезапись и живут в снапшотах/Free Space Map — vanish не даст гарантию «файла больше нет» на Btrfs/ZFS/APFS, пока существуют снапшоты; максимум — отказ или `--accept-cow` с явным предупреждением.
3. **Снапшоты vanish не удаляет.** VSS-тени, Time Machine, локальные APFS-снапшоты — данные пользователя; детект → warning, дальше действует пользователь (план §7, §12.3, §8).
4. **Резервные копии и облачные копии вне контроля.** vanish не находит и не стирает бэкапы и облачные версии (нецель N1). Любое обещание «файл исчез везде» — ложь.
5. **Страницы, выгруженные в своп/hibernate до начала стирания**, не могут быть молча «найдены и стёрты»; честный прогноз — предупреждение и флаг `swap_pages_possible`.
6. **Имена, осевшие в журнале/USN до запуска**, не гарантированно стираются; честная фиксация — флаг `journal_contains_old_names` (и опции очистки там, где они есть).
7. **Многопроходная перезапись — не противоядие против remanence-экспертизы (L3):** NIST SP 800-88 Rev.1 — «почти не даёт»; opt-in 3 прохода — опция совместимости, не гарантия.
8. **ФС вне списка (ReFS, неизвестные) и сетевые/overlay ФС** не получают никаких обещаний — только отказ (иначе это обещание было бы ложным).

### 5.4. Отчёт как механизм честности

Каждый запуск должен завершаться отчётом, по которому человек проверяет соответствие обещаний и фактов:

- поля: событие, скрытое имя (**только** хэш BLAKE3/SHA-256 или хвост `.vanish-v1-<hex16>`), strategy, bytes, warnings;
- флаги-ограничители: `ssd_chipoff_protected`, `journal_contains_old_names`, `swap_pages_possible` — присутствуют в каждом применимом отчёте;
- коды результата: 0 = ок; 1 = частично; 3 = отказ (неподдерживаемая ФС / занятость / хардлинк и другие отказные правила раздела 8); 4 = IO-неудача, включая любую неполную запись или неудачный fsync, которые никогда не маскируются под успех (инвариант 8);
- правило имён: исходное имя никогда не печатается в plaintext (инвариант 7), иначе отчёт сам становится форензическим артефактом (план §6).

## 6. Системные проверки / диагностика (`vanish check`)

### 6.0. Назначение и границы

- Команда `vanish check <path>` — read-only диагностика; она **ничего не пишет** на носитель и не меняет систему.
- Разрешены read-only системные утилиты для диагностики (решение из плана §0): fsutil, diskutil, tmutil, nvme, а также системные интерфейсы ОС (sysfs, /proc, WinAPI/реестр, ioctl-запросы). Никаких команд с побочными эффектами.
- Результат — человекочитаемый текст и/или JSON-отчёт (схема — будущий контракт): интерпретация уровня угроз, стратегия, предупреждения и флаги. check обязан «объяснять предел гарантий» (план §2): на незашифрованном SSD/COW честный ответ — «без возврата при L0–L2, нет гарантий против chip-off/L3».

### 6.1. Таблица проверок

| Проверка | Что смотрим | Вывод для пользователя | Поле/флаг отчёта |
|---|---|---|---|
| Поддержка ФС | Тип ФС тома (поддержана? каким способом?) | поддержана / отказ с кодом 3 (ReFS, неизвестные, NFS/CIFS/SMB/FUSE/overlay; tmpfs — своя строка матрицы) | strategy |
| Шифрование тома | LUKS (Linux), BitLocker (Windows, best-effort через WinAPI/реестр), FileVault (macOS) | зашифрован / не зашифрован / **Unknown** — если определить не удалось; «Unknown» вместо «Plain» — правило честности (план §12.2) | вход для `ssd_chipoff_protected` |
| Тип носителя | rotational / SSD; NVMe либо ATA; поддержка TRIM | задаёт стратегию deallocate и дисклеймер про chip-off | вход для `ssd_chipoff_protected` |
| COW-статус | Btrfs/ZFS/APFS | отказ без `--accept-cow`; честная формулировка предела | warnings |
| Снапшоты | VSS-тени, локальные TM-снапшоты (tmutil), APFS-снапшоты, снапшоты btrfs/zfs | предупреждение «копии существуют; сам инструмент их не трогает» | warnings |
| Журналы | Активный ext4-journal; NTFS $LogFile/USN; APFS-транзакции | имена могли осесть в журнале до запуска; для ext4 есть путь очистки журнала (root/unmount) | `journal_contains_old_names` |
| Своп | Активные swap-разделы/файлы (любая ОС); **особый случай — своп на той же ФС: отказ**; hiberfil.sys | предупреждение «страницы могли быть выгружены в своп»; рекомендация `--disable-swap-for-wipe` (root) | `swap_pages_possible` |
| Занятость (для целевых путей) | Открытые fd/мэппинги целевого инода: /proc/*/fd (Linux), FILE_SHARE_NONE (Windows), F_GETLK (macOS) | «файл открыт другим процессом или mmap'лен» → отказ с кодом 3 | warnings + код 3 |
| Политика хардлинков | st_nlink > 1 | «данные живы по другим путям»; каскадное удаление всех имён — только `--wipe-all-hardlinks` | warnings + код 3 |
| Системные пути | Списки отказа: `/`, `C:\`, `C:\Windows`, pagefile.sys, hiberfil.sys, swapfile.sys, System Volume Information, RegBack (Windows); `/System` и SIP-пути (macOS) | отказ без `--no-preserve-root` | warning + код отказа |
| Защищённость от chip-off | Сводный вывод: SSD? шифрование? | для SSD без полнодискового шифрования — «гарантии против chip-off нет» | `ssd_chipoff_protected` |
| «Лучшее достижимое» | Сумма всех предупреждений | объяснение пределов: «без возврата при L0–L2, нет гарантий против chip-off/L3» на SSD/COW | текст отчёта |

### 6.2. Разрешённые read-only утилиты (по платформам)

| ОС | Утилиты/интерфейсы | Что берём |
|---|---|---|
| Windows | fsutil, WinAPI, реестр | ФС, носитель, BitLocker-статус, VSS/USN-состояние |
| macOS | diskutil, tmutil | носитель, FileVault, локальные TM/APFS-снапшоты |
| Linux | nvme, sysfs, /proc (включая /proc/swaps) | TRIM/NVMe-состояние, LUKS-детект, своп |

Правило: только read-only; любая команда с эффектом записи вне wipe-режимов запрещена (то же правило входит в запрещённые зоны task-brief-ов, план §14.2).

### 6.3. Что check не делает

- Не удаляет снапшоты, не отключает своп, не чистит журналы — даже по запросу: это операции wipe-режимов с явными флагами и (где требуется) root/admin.
- Не даёт выводов об облачных копиях и бэкапах — таких данных у инструмента нет (нецель N1); поэтому не появляется ни «облако чисто», ни «бэкап стёрт».

## 7. Предположения

Гарантии vanish действуют при выполнении перечисленных ниже предположений. Если предположение нарушено, инструмент может выдать отказ (код 3) или IO-ошибку (код 4) — молчаливого «успеха» в нарушенных условиях не бывает.

### 7.1. Список предположений

| # | Предположение | Что означает | Если нарушено |
|---|---|---|---|
| A1 | Достаточные привилегии | Пользователь обладает правами на файл и каталог; операции уровня устройства/системы (FITRIM, отключение свопа, очистка журнала ext4, USN-очистка, device-wipe) запускаются с root/admin | Отказ или код 4; опции, требующие root, недоступны — инструмент честно укажет |
| A2 | Носитель исправен | Носитель не на пределе по износу; контроллер выполняет команды честно; fsync реально фиксирует данные | Операция не считается завершённой; verify не сходится → код 4, попытка не маскируется как успех (инвариант 8) |
| A3 | ОС не компрометирована | Нет руткита/малвари, перехватывающей системные вызовы и содержимое; компоненты ОС (файловые подсистемы, журнал, своп) работают по документированным правилам | Вне модели угроз; vanish не обещает защиты «от злой системы» |
| A4 | Нет внешнего вмешательства *во время* стирания | Другие процессы не изменяют и не пересоздают целевые файлы/пути в середине конвейера | Открытие/mmap чужим процессом → детект занятости → отказ с кодом 3; изменение содержимого → verify несходится → код 4 |
| A5 | Физический доступ оппонента ограничен | Для L0–L2 — никакого физического доступа к носителю; для L3/L4 — лаборатория работает с носителем **после** завершения стирания, а не во время | Физическое принуждение/вмешательство во время работы — вне модели; единственная защита — не начинать стирание в присутствии противника |
| A6 | Часы корректны | Системные часы (локальное время / UTC) не искажены: отчёты фиксируют время событий, оценка времени появления снапшотов, диагностика VSS/TM — используют системное время | В v1 время не участвует в криптографических решениях; искажённые часы искажают только отчёты/подсказки, но не безопасность самого стирания |
| A7 | ФС честно отвечает о себе | FIEMAP / FSCTL_GET_RETRIEVAL_POINTERS / APFS-метаданные возвращают согласованную картину экстентов на протяжении всего запуска | Расхождение → отказ/код 4; если ФС врёт систематически и это обнаружить нельзя — это предел best-effort-детекта (см. Unknown-правило) |
| A8 | Шифрование предшествовало данным | Если том зашифрован (LUKS/BitLocker/FileVault), шифрование было включено **до** записи стираемых данных — иначе старые plaintext-страницы могли физически осесть на носителе до включения шифрования | Отчёт не может это проверить автоматически; в спорных случаях — Unknown-подход и рекомендация «стереть ключ» + гигиена носителя |
| A9 | Объект не меняет тип между probe и стиранием | То, что проверено в шаге 1 (симлинк, ФС, инод), остаётся тем же объектом на шаге 5 | Анти-race по конструкции: переоткрытие через direct-handle со сверкой inode/FileId (план §6 шаг 5, §8) — расхождение → отказ |
| A10 | Пользователь действует осознанно | Для device-wipe пользователь подтверждает цель и проверяется «не смонтирован»; для опасных флагов (`--no-preserve-root` и пр.) — явный выбор | Инструмент запрашивает подтверждение; молчаливых разрушительных действий нет |

### 7.2. Что предположения НЕ меняют

- Предположения не «включают» защиту там, где физика её запрещает: они лишь квантифицируют, при каких условиях заявление уровня «достаточно» справедливо.
- Нарушение предположения никогда не превращается в скрытую деградацию: оно отображается в отказ, код 1/3/4 или предупреждение отчёта.

## 8. Правила отказа

### 8.0. Философия

- «Молчаливое частичное стирание» запрещено (план §13): hardlinks, открытые файлы, активный журнал без флага, своп без флага — всегда отказ или явное предупреждение.
- Отказ — это *успешное поведение инструмента*: он сохраняет исполнимость того, что обещано, вместо выполнения недообещанного.
- Верхнее правило: любой вопрос уровня «а что если не получится полностью?» решается в пользу отказа или честной пометки — никогда в пользу «сотрём то, что вышло».

### 8.1. Таблица отказных правил

| # | Условие | Правило vanish | Код выхода | Путь разрешения |
|---|---|---|---|---|
| 1 | Файл открыт другим процессом или mmap'лен | Детект занятости (fd/mmap целевого инода) → отказ, никакого частичного стирания | 3 | Закрыть процесс/мэппинг; повторить |
| 2 | У каталога/файла nlink > 1 | Отказ; предупреждение «данные живы по другим путям» | 3 | Только флаг `--wipe-all-hardlinks` (каскадное удаление всех имён) |
| 3 | Своп/hibernate зона на той же ФС | Отказ «иначе куски уйдут в своп» | 3 | Перенести своп/цель на разные тома вне vanish |
| 4 | Активный своп на *другом* разделе | Не отказ: детект → предупреждение «страницы могли быть выгружены»; флаг в отчёте | — (выполняем) | `--disable-swap-for-wipe` (root): отключить своп на время и восстановить |
| 5 | Активный журнал (ext4) без опции очистки | Отказ от *обещания* стирать имена в журнале: предупреждение + флаг; решение об отказе от всей операции уточняется контрактом (Приложение B, вопрос 2) | 3 | Опция очистки журнала ext4 — root/unmount (план §12.5); для NTFS — USN-очистка opt-in (admin) |
| 6 | COW-ФС: Btrfs/ZFS/APFS | Отказ: «старые экстенты в снапшотах» (APFS: «гарантия только FileVault + гигиена снапшотов») | 3 | `--accept-cow` — осознанный приём предела |
| 7 | Сетевые/overlay ФС: NFS/CIFS/SMB/FUSE/overlay | Отказ: «нет контроля блоков» | 3 | `--force-fs` — с полным осознанием отсутствия гарантий |
| 8 | ReFS и неопознанные ФС | Отказ: «неподдерживаемая ФС» | 3 | Нет (выбор ФС вне vanish) |
| 9 | Системные пути Windows: `C:\Windows`, pagefile.sys, hiberfil.sys, swapfile.sys, System Volume Information, RegBack | Отказ — защита пользователя от себя | 3 | Нет (вне продукта) |
| 10 | macOS: `/System` и SIP-системные пути | Отказ | 3 | Нет |
| 11 | Корень диска `/`, `C:\` | Отказ без `--no-preserve-root` | 3 | `--no-preserve-root` — явно и на свой риск |
| 12 | Цель — симлинк, переопределение (reparse), read-only, immutable (chattr+i / readonly-файл) | Отказ на probe-этапе (план §6 шаг 1, §14) | 3 | Снять условия вне vanish; повторно probe |
| 13 | Неполная запись / неудачный fsync / расхождение verify | Прерывание попытки; никогда не маскируется как успех | 4 | Повторить; проверить носитель (инвариант 8) |
| 14 | Прерванный запуск (kill -9 и пр.) | Хвост `.vanish-v1-*` остаётся на диске — и это по построению: recovery-механизм `--recovery-scan` находит и «дожимает» хвосты | 0/1 | Запустить `--recovery-scan` |
| 15 | ADS/xattr/resource fork присутствуют, флаг `--keep-streams` задан | Не отказ: стирание основной записи идёт, потоки остаются; отчёт фиксирует решение пользователя | 0/1 | По умолчанию потоки стираются всегда (план §0) |

### 8.2. Флаги-разрешения (opt-in override-и)

| Флаг | Что разрешает | Цена для пользователя |
|---|---|---|
| `--accept-cow` | Начать стирание на COW-ФС (Btrfs/ZFS/APFS) | Старые экстенты остаются в снапшотах; отчёт это фиксирует |
| `--force-fs` | Работать на NFS/CIFS/SMB/FUSE/overlay | Нет контроля блоков; гарантии нет |
| `--no-preserve-root` | Разрешить цели «корень диска» | Потенциальная потеря системы |
| `--wipe-all-hardlinks` | Каскадное удаление всех имён при nlink > 1 | Все пути к данным будут стёрты |
| `--disable-swap-for-wipe` (root) | Временно отключить своп ради стирания | Своп восстанавливается после; во время стирания ОС может вести себя иначе |
| `--keep-streams` | Не стирать ADS/xattr/resource fork | Потоки-тайники остаются (исключение из правила «всегда») |
| опция журнала (ext4) | Очистка журнала | Требует root/unmount (план §12.5) |
| `--passes`, `--pattern`, Gutmann-опции | Мультипроходные паттерны | Не даёт приращения гарантируемости против L3 — opt-in для совместимости, не маркетинг |

### 8.3. Коды выхода (план §9)

| Код | Значение |
|---|---|
| 0 | Успех «как обещано» |
| 1 | Частично: выполнено, но с предупреждениями/с исключениями (флаги, `--keep-streams` и пр.) |
| 2 | Ошибка использования (CLI) |
| 3 | Отказ: неподдерживаемая ФС, занятость/хардлинк и прочие отказные правила из 8.1 |
| 4 | I/O-неудача: неполная запись, неудачный fsync, верификация не сошлась |

Примечание: точный отбор кода 2 против 3 для отдельных сценариев (системные пути, корень диска) уточняется контрактом — вопрос занесён в Приложение B.

## 9. Глоссарий

Канонические термины проекта. Их определения совместимы с формулировками PLAN.md; в отчётах и сообщениях используются именно эти слова.

| Термин | Каноническое значение |
|---|---|
| Перезапись | Управляемая запись поверх данных по их экстентам (overwrite): 1 проход + verify — норма NIST SP 800-88; многопроходность — opt-in, не дефолт. «Сброс на носитель» после каждого прохода — обязательный элемент перезаписи |
| Verify | Проверочное чтение записанных данных (без кэша) с сопоставлением с записанным паттерном; несоответствие — код 4 |
| Dealloc (deallocate) / TRIM | Освобождение блоков на носителе: для SSD — подсказка контроллеру, что логические блоки становятся ненужными (per-file TRIM, FITRIM на Linux, storage-optimization на Windows, аппаратное стирание на macOS). Подсказка ≠ гарантия физического стирания |
| Punch-hole | «Пробивание дырки» в файле: физическое освобождение блоков в заданном диапазоне — FALLOC_FL_PUNCH_HOLE (Linux), FSCTL_SET_ZERO_DATA (Windows), truncate (macOS). Шаг 8 конвейера для SSD |
| COW (copy-on-write) | Файловая система, где перезапись всегда создаёт новый экземпляр блока, а старый остаётся на месте (Btrfs/ZFS/APFS): старые экземпляры живут в снапшотах/Free Space Map. Vanish против COW — отказ или `--accept-cow` |
| FTL | Flash Translation Layer — внутренний словарь контроллера SSD «логический блок ↔ физическая страница» + wear leveling. Причина, почему перезапись файла не трогает старые физические страницы (L4) |
| Over-provisioning | Резервный запас страниц SSD вне адресуемого пространства, куда FTL складывает старые версии данных. Недоступен ОС; корневая причина флага `ssd_chipoff_protected: false` |
| Wear leveling | Равномерное распределение износа: контроллер постоянно переносит данные между страницами, множая «старые» копии |
| SANITIZE / CRYPTO_ERASE | Устройство-уровневые средства уничтожения (NVMe Sanitize / ATA Secure Erase): первичный путь стирания устройства целиком (`vanish device`). CRYPTO_ERASE — вариант, стирающий ключ шифрования устройства: быстрый, но требует, чтобы данные были зашифрованы самим накопителем |
| BLKDISCARD | Команда «эти диапазоны не нужны» для блочного устройства; только fallback стирания устройства целиком, с предупреждением «физическое не гарантировано» (план §7) |
| Journal (журнал ФС) | Журнал транзакций файловой системы: ext4 journal, NTFS $LogFile/USN, APFS-транзакции. Имена и фрагменты могли осесть ДО запуска vanish — отсюда флаг `journal_contains_old_names`; полная очистка ext4-журнала — отдельная опция (root/unmount) |
| Инод | Индексный дескриптор файла: структура метаданных, остающаяся до переиспользования после unlink |
| Экстент | Непрерывный диапазон блоков файла; карта экстентов берётся FIEMAP / FSCTL_GET_RETRIEVAL_POINTERS (macOS: весь файл) |
| Page cache | Кэш страниц ОС (содержимое и метаданные). Vanish пишет мимо кэша и завершает drop-caches-эквивалентом (FADV_DONTNEED / NO_BUFFERING / F_NOCACHE) |
| Своп | Пространство выгруженных страниц (swap-раздел/файл Linux, pagefile.sys/swapfile.sys Windows, директории свопа macOS); плюс hiberfil.sys. Не адресуем vanish'ем; флаг `swap_pages_possible` |
| ADS / xattr / resource fork | Дополнительные потоки данных файла: NTFS ADS (Zone.Identifier и пр.), Linux/macOS xattr, macOS resource fork. Стираются всегда по умолчанию; opt-out `--keep-streams` |
| VSS-тени | Теневые копии тома Windows (System Volume Information). Vanish их не уничтожает: детект → warning («сам их не трогаем») |
| Time Machine / APFS-снапшоты | Копии macOS (внешний TM-диск / локальные снапшоты). Детект → warning; уничтожение — на пользователе |
| Remanence | Остаточная намагниченность HDD (L3): то, что может прочитать специализированная лаборатория; по NIST SP 800-88 Rev.1 многопроходность «почти не даёт» |
| Chip-off | Снятие/чтение NAND-чипов напрямую, минуя контроллер (L4). Первичное средство — полнодисковое шифрование + уничтожение ключа |
| LUKS / BitLocker / FileVault | Полнодисковое/внутритомное шифрование Linux / Windows / macOS (LUKS, BitLocker, FileVault). Vanish детектирует шифрование тома; «не определили» → Unknown, а не Plain |
| Clear / Purge (NIST SP 800-88) | Категории стирания: логическая (Clear) и аппаратно-контролируемая (Purge). Логическая основа стратегии «достаточно» для HDD |
| Хвост `.vanish-v1-<hex16>` | Единый именной хвост временного имени на всех ОС: rename прячет оригинальное имя под ним; recovery-скан ищет именно этот паттерн |
| Marker-oracle | Тест-метод QA: маркерные паттерны по смещениям на сырой поверхности; после wipe — критерий 0 совпадений + PhotoRec/testdisk возвращают ноль (план §10, §14.4) |

## 11. Приложение B. Открытые вопросы к оркестратору

Вопросы, которые должны быть закрыты контрактом (`docs/contract/contract.md`) до заморозки:

1. **Код выхода для системных путей.** План §9 различает 2 (usage) и 3 (неподдерживаемая ФС/занятость/хардлинк), но не указывает код для отказа на `/`/`C:\` и системных файлах Windows/macOS. Рекомендация: 3 с текстом отказа; окончательно решает контракт.
2. **Поведение при активном ext4-журнале без опции очистки.** План §13 допускает «отказ или явное предупреждение». Нужно одно решение; рекомендация — отказ с кодом 3, потому что стирание имён без очистки журнала честно не обещается.
3. **Статус опции очистки ext4-журнала.** Упоминается в рисках (план §12.5), но отсутствует в списке флагов CLI (план §9). Контракт должен либо добавить флаг в CLI-спецификацию, либо зафиксировать механику иначе.
4. **Семантика `ssd_chipoff_protected` для HDD.** План вводит флаг в контексте SSD. Предложение: false только для SSD без полнодискового шифрования; для HDD — true (chip-off не применим). Требует фиксации в контрактной JSON-схеме.
5. **Приоритет переопределяющих флагов.** Комбинации `--accept-cow` / `--force-fs` / `--no-preserve-root` / `--wipe-all-hardlinks` в опасных сочетаниях не специфицированы; контракт должен определить порядок применения и требуемые подтверждения.
6. **Комментарий о бэкапах/облаках в отчёте.** Должен ли каждый отчёт содержать статическую строку-напоминание «бэкапы/облако не охвачены» (без детекта)? В плане нет; без решения оркестратора не вводим (не изобретаем функции).
7. **Contract.md не существовал на момент написания.** После его появления — сверить термины, JSON-схему отчёта (флаги `ssd_chipoff_protected`, `journal_contains_old_names`, `swap_pages_possible`) и случаи из этого документа с контрактом; расхождения — через оркестратора, change log контракта (план §14.3).
