# Реальный план «тотальной санитарной чистки»

Дата: 2026-10-22. Статус: план и протокол верификации; не заявление о достигнутой
невосстановимости.

## Главная честная рамка

**Абсолютное «без возможности какого-либо восстановления» недостижимо и никогда
не заявляется.** FTL/wear-leveling и over-provisioning SSD, журналы ФС,
снапшоты COW/VSS/Time Machine, резервные копии и облака, swap/hibernate,
xattr- и журнальные копии, remapped sectors HDD — это свойства среды, а не
кода. Проект продаёт **доказанные уровни**, а не обещания.

## Лестница уровней G0–G5

| Уровень | Содержание | Доказательство |
|---|---|---|
| G0 | Логический unlink: запись каталога снята, блоки живы | контроль: photorec файл НАХОДИТ (unlink ничего не гарантирует) |
| G1 | Логическая перезапись достижимых экстентов + rename→truncate→unlink | raw-скан O_DIRECT: 0 маркеров; PhotoRec: 0 файлов |
| G2 | G1 + учёт журналов/COW: отказ или явный caveat | debugfs logdump до/после; контроль снапшотов |
| G3 | G2 + wipe свободного места (freespace) | маркеры после plain `rm` исчезают из raw-скана |
| G4 | Полная перезапись устройства (BLKGETSIZE64, N проходов, sync, readback) | полный raw-скан устройства = 0 маркеров |
| G5 | Sanitize/crypto-erase: ATA Secure/Enhanced Erase, NVMe Format/Sanitize, BLKSECDISCARD, уничтожение ключа LUKS/SED | nvme sanitize-log, hdparm -I, smartctl до/после + G4-скан |

## Где vanish сейчас

- **G1** — реализовано и покрыто тестами; в отчёте заявляется как
  `guarantee_level=G1` только при достоверно отсутствующем журнале
  (`JournalState::None`). Если журнал Active или Unknown — `content-only`.
  Подтверждено полигоном на loop-ext4 без журнала (2026-10-22).
- **G2** — частично: shared/encoded extents отвергаются fail-closed, журнал
  честно отражается как `journal_contains_old_names`, COW требует `--accept-cow`.
  Журнальный прогон 2026-10-22 подтвердил: содержимое и PhotoRec чисты, но
  имена-хвосты остаются в журнале. Это зафиксированная граница, а не G2.
- **G3** — freespace реализован; полигон-кейс 7 пройден на ext4 без журнала и
  с журналом (content-маркеры после `rm` исчезают).
- **G4/G5** — device-режим ЗАБЛОКИРОВАН в CLI и backend до выполнения чек-листа.
- Заявлять можно максимум G1(+G3) для файлов на проверенном loop-ext4 без
  журнала; с журналом — только content-санитизацию с оговоркой об именах.
  Для остальных ФС/носителей — только после отдельных прогонов.

## Полигон (запускает пользователь, root, изолированный loop)

Скрипты `tests/polygon/` образуют fail-closed протокол. Они **не устанавливают
пакеты** и работают только со своим приватным состоянием в
`/var/lib/vanish-polygon` (lock, проверка идентичности loop/image, O_DIRECT-скан,
64+128 маркеров положительного контроля, PhotoRec — автоматически или вручную).

### Что нужно установить вручную

- Обязательно: `util-linux`, `e2fsprogs` (есть почти везде).
- Для полного PASS: `testdisk` (даёт `photorec`). Без него прогон честно
  остановится на INCOMPLETE (код 2) после raw-проверок.
- Полигон требует root и ~1 ГиБ свободного места в `/var/lib` (образ 256 МиБ +
  raw-копии сканов). Работает только со своим loop-образом; ваши диски не
  затрагиваются. **Не запускайте на системе, где `/var/lib` или `/` доступны
  на запись недоверенным пользователям.**

### Команды

```bash
cargo build --release --locked        # или укажите свой доверенный бинарь
sudo bash tests/polygon/run_all.sh target/release/vanish --auto-photorec
# вариант с журналом (ожидаемый провал скана имён — честная граница):
sudo bash tests/polygon/run_all.sh target/release/vanish --with-journal --auto-photorec
sudo bash tests/polygon/teardown.sh   # уборка после каждого прогона
```

### Интерпретация

- `PASS (full)` (код 0): raw-сканы чисты и PhotoRec восстановил 0 файлов.
  Это доказательство G1+G3 на loop-ext4 (без журнала либо с оговоркой журнала).
- `INCOMPLETE` (код 2): raw чисто, но PhotoRec не выполнен/не доказан. Это НЕ
  PASS. Доведите форензику до конца или считайте результат недоказанным.
- `FAIL` (код 1): маркеры/хвосты остались либо PhotoRec что-то восстановил.
  Артефакты в `/var/lib/vanish-polygon/run.*` — пришлите логи.
- В `--with-journal`: `EXPECTED-FAIL` для имён-хвостов — задокументированная
  граница (журнал не стирается), контент-маркеры обязаны быть чистыми.

### Результат первого прогона (2026-10-22)

- `run.VcWfa5MTinaZ`: loop-ext4 **без журнала**, 256 МиБ, все 7 кейсов `rc=0`,
  `status=photorec-clean`.
- Raw-скан через `O_DIRECT`: `VANISH_ORACLE` — 0 вхождений,
  `.vanish-v1-` — 0 вхождений.
- PhotoRec 7.2 (scripted, `partition_none,search`): `Total: 0 files found`,
  восстановленных файлов нет.
- Вывод: **G1+G3 подтверждены для этого loop-образа ext4 без журнала**.
  Это не доказывает G2 (журнал), G4/G5, реальные HDD/SSD, snapshots или
  физическую невосстановимость.
- Полные логи остаются в `/var/lib/vanish-polygon/run.VcWfa5MTinaZ` (root-only);
  в репозиторий они не добавлялись.
- Следующий обязательный прогон: тот же протокол с `--with-journal`, чтобы
  зафиксировать честную границу остатков имён в журнале.

### Результат журнального прогона (2026-10-22)

- `run.6dXxJcQWPulA`: loop-ext4 **с журналом**, 256 МиБ, все 7 кейсов `rc=0`.
- Raw-скан через `O_DIRECT`: `VANISH_ORACLE` — 0 вхождений;
  `.vanish-v1-` — `EXPECTED-FAIL` (имена-хвосты сохраняются в журнале).
- PhotoRec 7.2 (scripted): `Total: 0 files found`, восстановленных файлов нет.
- Итог: `PASS (content only, with-journal)`, `rc=0`. Это доказывает удаление
  содержимого в пределах смонтированной ФС, но **не G2**: журнал ext4 сохраняет
  старые имена. Для G2 нужен внешний journal wipe/пересоздание ФС или честный
  отказ; текущий код их не выполняет.
- Логи остаются в `/var/lib/vanish-polygon/run.6dXxJcQWPulA` (root-only).

## Дорожная карта

- **M1.** Прогон полигона пользователем (оба варианта), фиксация сводки в
  этом документе и QA; полные root-only логи остаются на машине. **Выполнено
  2026-10-22 для loop-ext4 без журнала и с журналом.**
- **M2.** Этот документ + синхронизация README/threat-model; честная матрица
  уровней по ФС (см. таблицу выше) — сделано в этом цикле.
- **M3.** Поле `guarantee_level` в отчёте и матрица в `check`; G2/G4/G5 не
  заявляются. **Выполнено:** значения `G0/G1/G3/content-only/none`, причины —
  `guarantee_ceiling`/`guarantee_notes`.
- **M4.** Read-only preflight устройства: **выполнено на уровне API и
  `device --dry-run`** — идентичность через `rdev` и `/sys/dev/block`, размер
  из sysfs (без `BLKGETSIZE64`/`open`), holders/slaves, swap, mountinfo,
  boot-связь; `execution_allowed=false`, blockers всегда включают
  «device execution disabled». Учтены btrfs-multi-device: mount-строки
  сопоставляются и по source-пути (с отсечением `[/subvol]`), членство в
  btrfs проверяется через `/sys/fs/btrfs/*/devices`. Типизированное
  подтверждение и любой execution относятся к M5/M8; для whole-disk нужен
  учёт дочерних разделов.
- **M5.** Execution на loop-only: многопроходная перезапись + readback verify.
- **M6.** Транспорты: NVMe sanitize ioctl, ATA через hdparm, BLKSECDISCARD;
  обработка frozen/timeout; «прерванный sanitize = неизвестное состояние».
- **M7.** Железные прогоны пользователя на одноразовых USB/HDD/NVMe по
  протоколу G4/G5 (маркеры, smartctl/hdparm/nvme логи, PhotoRec).
- **M8.** Снятие блокировки device-режима только после M4–M7 с evidence.

## Что не входит в план (явный отказ от обещаний)

- Уничтожение данных в журналах, снапшотах, бэкапах, облаках, swap/hibernate.
- Победа над FTL/remap без sanitize/crypto-erase.
- Кросс-платформенные гарантии (macOS/Windows — заглушки).
- «100% невосстановимо» — формулировка запрещена; только уровни G1–G5 с
  доказательствами конкретного прогона.
