# vanish — CLI удаления файлов на Rust

vanish выполняет логическую перезапись и удаление файлов, выбирая стратегию по
свойствам файловой системы. **Успешный запуск не доказывает невозможность
восстановления всех исторических физических копий данных.** Снапшоты, журналы,
резервные копии, remapped sectors и внутреннее управление NAND могут сохранять
данные вне адресуемого программой файла.

## Статус безопасности

Текущая ветка содержит исправления аудита после исторического `v1.0-linux`.
Она **не сертифицирована для критичных данных**. В частности:

- destructive-режим `device` временно заблокирован и в CLI, и в Linux API;
- не используйте привилегированный запуск над путями, которые может менять
  другой пользователь: полная защита namespace от конкурентных подмен ещё
  не реализована;
- `/proc`-проверка открытых файлов не гарантирует отсутствие mmap, скрытых
  процессов или новых держателей после проверки;
- wipe требует возможности прочитать `/proc/<pid>/fd` всех процессов (обычно
  root или `CAP_SYS_PTRACE`). Если fd процесса другого UID недоступен,
  busy-проверка неполна и wipe отказывается (код `4`). `check` в этом случае
  выдаёт диагностику с предупреждениями, а не отказ всего запуска;
- Windows/macOS-бэкенды остаются заглушками;
- ранее собранные файлы в `dist/` сами не обновляются при изменении исходников.
  Пересоберите программу перед использованием исправлений.

Модель угроз и план в `docs/` содержат также проектные требования, а не только
реализованные гарантии. Исторические QA-вердикты относятся к указанным там
сборкам и ограниченному полигону, а не ко всем носителям.

## Сборка и проверки

Требуется Rust **1.85 или новее** для текущего `Cargo.lock`.

```bash
cargo test --workspace --locked
cargo test --workspace --release --locked
python3 scripts/test-security.py
bash scripts/security-audit.sh

# Сначала release-тесты, затем сборка, необязательный UPX и SHA256SUMS:
bash scripts/build-release.sh
dist/vanish --selfcheck
```

UPX только сжимает бинарь; это не шифрование и не проверка подлинности.
`--selfcheck [MANIFEST]` сверяет SHA-256 файла программы с манифестом. Источники:
явный путь, `VANISH_SHA256SUMS`, затем `SHA256SUMS` рядом с exe. Если явно
указанный источник отсутствует, скрытого перехода к другому манифесту нет.
Проверка **не защищает от замены одновременно бинаря и неподписанного манифеста**.
Для проверки поставщика нужен независимо доверенный или подписанный манифест.

Коды selfcheck: `0` — хэш совпал, `1` — не совпал, `2` — манифест отсутствует,
`4` — ошибка проверки.

## Использование

Обычное удаление необратимо и не спрашивает подтверждения. Начните с плана:

```bash
dist/vanish --dry-run /path/secret.bin
dist/vanish --verify /path/secret.bin
dist/vanish --json /path/stuff/
dist/vanish --json --report /safe/new-report.json /path/stuff/
```

`--report` создаёт **новый** файл; существующий файл или симлинк не
перезаписывается. Храните отчёт вне удаляемого дерева. Ошибка подготовки отчёта
должна останавливать операцию до удаления. `--json` и `--report` можно сочетать.
При dry-run допускается создание явно запрошенного нового отчёта; сами цели
и свободное место не изменяются.

Флаги:

- `--passes N`, `--pattern random|zero|gutmann|hex:XX`: проходы и паттерн
  (`hex:XX` допускает не более 16 проходов, иначе ошибка аргументов);
- `--verify`: проверять записанное после sync; по умолчанию проверка выключена;
- `--no-rename`: не переименовывать цель в `.vanish-v1-*`; recovery не сможет
  найти хвост по имени, хотя файл всё равно будет удалён;
- `--accept-cow`: разрешить логическое удаление на Btrfs/ZFS **без обещания
  уничтожения старых блоков или снапшотов**;
- `--wipe-all-hardlinks`: разрешить обработку inode с несколькими именами.
  Другие имена автоматически не ищутся и не удаляются, но их содержимое
  меняется вместе с общим inode. Отчёт выводит предупреждение, что остальные
  имена не сняты;
- `--xdev`: не переходить границы файловых систем при обходе дерева;
- `--no-trim`: отключить per-file punch-hole; `--trim`: запросить FITRIM;
- `--force-fs`: явный обход политики неподдержанной ФС с непроверенными
  гарантиями; не превращает best-effort в физическое санитирование и **не
  отключает защиту `/proc`, `/sys`, `/dev`, `/run`** — она действует всегда;
- `--disable-swap-for-wipe`: временно недоступен. При необходимости отключите
  swap внешними средствами и повторите диагностику.

Псевдо-ФС всегда запрещены. По умолчанию разрешены конвейеры для
ext4, XFS, FAT/exFAT, tmpfs/ramfs и, с отдельным принятием COW, Btrfs/ZFS.
Это список логических стратегий, **не сертификат физического удаления**.
F2FS, неизвестные и другие непроверенные ФС требуют явного override.
Даже XFS может иметь shared/reflink extents: уничтожение исторических копий
текущими проверками не доказано.

### Дополнительные режимы

```bash
dist/vanish check /path                  # read-only диагностика
dist/vanish --dry-run freespace /data --size 1048576
dist/vanish freespace /data --size 1048576
dist/vanish recovery /path               # повторная обработка хвостов
dist/vanish --recovery-scan /path
dist/vanish device /dev/sdX --dry-run     # только preflight, без open/ioctl
```

Без `--size` freespace использует бюджет 95% доступного места. Это может
временно заполнить том и мешать другим программам; используйте изолированный
том. `--size` допустим только в этом режиме; другие команды отвергают его как
ошибку аргументов. Заполнение свободного места на COW/SSD не доказывает
перезапись старых физических блоков. При ошибке записи или SIGINT
скретч-файл удаляется (в том числе fallback-unlink, если wipe-конвейер уже
отказал); гарантий при SIGKILL/потере питания нет. `device` по умолчанию
возвращает отказ (`3`); при `--dry-run` выполняется только read-only preflight
(метаданные, `/sys`, mountinfo, swaps — без `open`/ioctl) и перечисляются
блокеры. Destructive-исполнение разрешено **только для loop-устройства** и
только при одновременных `--device-wipe-loop --confirm-device <PATH>`; путь
подтверждения должен канонически совпадать с устройством, иначе код `2` до
открытия. Успех — код `0`, `guarantee_level=content-only`,
`physical_guaranteed=false`: перезаписывается loop-backing файл, но физическое
уничтожение и COW/sparse-копии не доказываются. Для реальных дисков execution
остаётся заблокированным.

При SIGINT текущий файл полностью заканчивается, включая оставшиеся экстенты
и проходы; следующие цели не начинаются. Для большого файла ожидание может
быть долгим. SIGKILL и потеря питания этим механизмом не обрабатываются;
recovery повторяет обработку обнаруженных хвостов, но не является доказательством
полного восстановления транзакции после любого сбоя.

## Результаты и приватность

| Код | Значение |
|---|---|
| 0 | запрошенные операции завершены, либо получен dry-run-план |
| 1 | частичный результат: rejected вместе с ok, skipped вне dry-run или прерывание с необработанными целями |
| 2 | ошибка аргументов |
| 3 | отказ политики (все цели отвергнуты) |
| 4 | ошибка выполнения, IO, проверки или вывода отчёта |

Отчёт `vanish.report.v1` использует `name_hash` и recovery-хвосты вместо
исходных имён. SHA-256 пути без соли не обеспечивает анонимность: известные
или предсказуемые пути можно проверять перебором. Храните отчёты как
потенциально чувствительные метаданные. Флаги `encrypted_at_rest` и подобные
являются результатами диагностики, а не подтверждением уничтожения ключей.
Отдельный диагностический `check` выводит также mount/device, swap-пути и
данные процессов; его JSON не имеет тех же ограничений приватности, что
wipe-отчёт. Не публикуйте его без проверки. `check` обрабатывает каждую цель
отдельно: недоступные `/proc`-данные или ошибки FS дают запись с
предупреждением и пометкой «диагностика неполна», а не ложный успех; реальные
отказы политики остаются отказами. `check` учитывает переданные флаги
(`--accept-cow`, `--xdev` и т.п.), а не только настройки по умолчанию.

У каждой цели wipe-отчёта есть `guarantee_level`: `G0` — только снятие имени
(каталоги), `G1` — содержимое перезаписано при достоверно отсутствующем
журнале, `G3` — заполнение свободного места без журнала, `content-only` —
операция успешна, но содержимое или имена могут сохраняться (COW, tmpfs,
журнал Active/Unknown), `none` — план, отказ, ошибка или пропуск. Уровни
G2/G4/G5 не заявляются. `check` печатает `guarantee=` и причины; это потолок
для конкретной цели, а не сертификат носителя.

## Ограничения и дальнейшая работа

- Журналы ext4 и других ФС могут сохранять имена и данные; vanish их не стирает.
- Удаление xattr не доказывает уничтожение прежних значений metadata.
- TRIM/punch-hole не равнозначны NVMe Sanitize или ATA Secure Erase.
- Шифрование тома само по себе не означает выполненный crypto-erase.
- Требуются дополнительные испытания namespace-races, shared extents,
  power-loss, реальных HDD/SSD и отказов системных вызовов.

Текущие решения и оставшиеся ограничения: `docs/security-hardening.md`.
Протокол регрессионных проверок: `docs/qa/hardening-checks.md`.
Реальный план к «тотальной чистке» и уровни гарантий: `docs/sanitization-plan.md`.
Полигон требует root и отдельной проверки окружения: **не запускайте его
на рабочем томе**. Исправления скриптов не заменяют изоляцию испытаний.
